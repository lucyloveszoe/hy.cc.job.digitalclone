Initiated 02/21/2024 as "WSD Logistics Data Integrity" per a request from Wingra, later renamed **IDI (Integrity Data Infra)**. Owners: Chao/Jiapeng (with KinLum). Problem framed by KP as a classic "day-1" cross-vendor design-tool integration gap: WSD's design flow spans multiple vendor tools (ADS, Cadence, Allegro) with inconsistent naming/formats, so die-layout footprints, PCB/SIP footprints, HFSS components, and EBR (assembly) diagrams drift out of sync — symbols get mixed up, pin numbering doesn't match, obsolete footprints get reused. Wingra's ask: a central database (cloud-hosted, WSD owns technical ownership) that each design tool/role can pull the *current* footprint/symbol from, plus an API and partial web UI, plus visualization for part of the data.

**Scale cited by Wingra (Feb 2024)**: ~166 users checking out SIP-footprint licenses, ~117 unique HFSS-component users, ~175 unique IC-layout users, plus "likely the whole test team" for the EBR side — i.e. this touches most of WSD's hardware design/NPI population, not a niche tool.

**Scope/phasing (per Wingra's multi-phase proposal, shared by 03/26/2024 — correcting an earlier "~mid-2024" estimate)**: Phase 1 = Die Tapeout Process; Phase 2 = "Detour" (further phases undefined at this point). Chao/Jiapeng ran PCB SIP data collection work as part of Phase 1 (clarifying cloud-vs-Broadcom hosting and DB-direct-access-vs-API questions with Wingra).

**Kickoff confirmed 03/26/2024**: Wingra shared the Phase 1 ("Die Tapeout Process") SOW draft and the multi-phase proposal; kickoff was confirmed per Wingra/Lea-Teng (Strategic Planning) and John Kim (Design Automation) — Lea-Teng and John Kim had already agreed on the design/post-tapeout ownership split (WSD handles after-tapeout, design team handles the design portion). Wingra planned to start the SIP work April/May 2024 to demonstrate early ROI before tackling later phases, with a phases-proposal review meeting scheduled 04/01/2024. Wingra also flagged confidential-data-access concerns to be worked through as part of the SOW.

**Phase 1 target set to 06/28/2024, ROI framing and architecture settled (04/01-04/09/2024)**: Lea-Teng gave KP the ROI justification — Phase 1 end users are the NPI backend team (planning/EBR/wafer-probe/product test); Phase 2 is the system-simulation/test team (linking test data to EBR); Phase 3 (long-term) links EBR+test data to simulation. Lea-Teng formally introduced the project to the end-user community 04/05/2024 (attendees: SW owners Chao/Jiapeng/KinLum; Wingra/Lea-Teng as PM; DA producers John/Mike; process masters Gary/Aruna). Technical pivot: the original web-form upload design couldn't handle bulk (100+ files, wide size range) uploads in one API call, so the team switched to an **S3 presigned-URL** upload architecture (web portal does an AJAX PUT to the presigned URL; API path adds concurrency-controlled parallel uploads) — OKTA integration still required since front end/API must sit in the BRCM domain. Internal SRS review scheduled 04/18/2024, completed with all stakeholders 04/30/2024, moving into Development stage; official dev kickoff (shared with Wingra) 04/19/2024. By ww19 (05/07/2024) the item's display name had shifted to "IDI Phase 1: Footprints (Die & General)" — same Phase 1 scope, not a new phase. **Target date slipped from 06/28/2024 to 08/02/2024** (change visible starting ww20/05/14/2024; no explicit reason logged, but consistent with SRS review/dev-kickoff and VM-provisioning work still running through mid-May). By 05/14/2024, 3 VM servers were provisioned in the LVN data center and IIS/OKTA-authenticated web portal setup was underway.

**Scope boundary decision — Wingspan DB integration into IDI dropped (04/30/2024), correcting earlier framing**: at Wingra's request, Kin Lum had separately authorized her as root/owner of a new "Wingspan DB" hosted on WSD's Aurora (Oregon), intended to let Wingra migrate/"clone" her team's existing Airtable data into a proper SQL database (Airtable isn't 100% SQL-compatible, so a straight clone isn't possible). Wingra then wanted IDI itself to reference/query this Wingspan DB as a linked data source — **this was explicitly dropped after discussion with Wingra/Yu Han**: "IDI is a pure multi-users data exchange platform, what can be query/search/download by consumers are decided by producers' upload, no need to reference to separate data source... might be necessary in the future, definitely not at this moment." The Wingspan-DB line item itself was also marked "(Drop)" in the IDI report's non-development tracking around this time and had disappeared from the tracking list entirely by ww22 (05/28/2024) — so treat "WSD's Aurora footprint keeps absorbing other teams' databases" as **not an active, confirmed-growing precedent**; the Wingspan DB itself may still exist standalone, but its planned integration into IDI did not proceed. Distinct from the IDI DB itself (which stores only file metadata under SW team control and was unaffected by this decision).

**Phase 1 confirmed released 08/06/2024**: code frozen 07/30/2024, IaC production deployment completed in us-west-2 07/30/2024, buy-off confirmation received from Wingra 07/31/2024, and the SDD finalized 08/06/2024 (target date had been 08/09/2024, so this shipped slightly early). Live portal: `http://wpdvfabpcb01.lvn.broadcom.net/index.html`. This supersedes the earlier "implying a release milestone" framing — Phase 1 (Die Tapeout Process) is a confirmed, dated completion, not an inference.

**Status at year-end 2024**: Subsequent phases are tracked as **"IDI Phase-N" and marked Hold** with no firm target date, and a further delay was reported by Wingra/DA as recently as 12/17/2024.

A fuller phase list surfaced 01/07/2025: Phase 1 = Die Tapeout Process; Phase 2 = "Detour"; an unspecified further phase = 3D Components; Phase 3 = Module Tapeout; Phase 4 = EBR — pending a 04/01 review (year not specified in source, presumed 2025).

**Why:** a substantial, multi-hundred-user cross-tool data-integrity initiative that WSD SW team took technical ownership of at Wingra's request — distinct from WSD's own production-test data pipeline work (zDB/WUDAS/Clotho), this is design-side (pre-production, NPI/R&D) data.

**How to apply:** search for "IDI" or "Integrity Data Infra" (not "WSD Logistics Data Integrity") when looking for later updates — the project renamed early in its life. Treat Phase 1 (Die Tapeout) as likely shipped by mid-2024; treat later phases as stalled/on-hold as of the most recent record (Dec 2024) — verify current status before assuming further progress.

**Sensitive-design-data clarification (08/13/2024)**: in response to a data-protection question, Yu Han clarified IDI uses a *passive* collection model — IDI itself never decides whether an uploaded entry is confidential, but if an uploader flags a specific entry as confidential, IDI simply won't generate an upload/download URL for it. Wingra and KP confirmed the actual data volume/sensitivity is low: only footprints, symbols, keepouts, and die/pad dimensions for EBR tapeout are stored — no GDS files, schematics, routing, or transistor-level design data ever enters IDI. Useful baseline if a future security/compliance question about IDI's data-sensitivity posture comes up.

**Earlier, narrower auth-relaxation precedent — Okta disabled for Cadence upload path (09/10-09/17/2024)**: John (design/Cadence side) requested bypassing Okta login specifically for the *upload* API called from the Cadence system, with Wingra raising concerns. Yu Han's framing (which recurs in the 02/04/2025 decision below): IDI needs *some* ID for two purposes only — activity tracking and access control — and it doesn't matter which ID mechanism satisfies both. Since a shared/generic Cadence account might not, but full Okta auth was impractical for this call path, the resolution was a middle ground: **pass `user_id` via an HTTP header** instead of requiring Okta login; IDI's normal ACL check then runs against that header value. Explicitly flagged risk: a generic/shared `user_id` means weak ACL control in practice. Yu Han additionally required the error-recovery/rollback mechanism (version snapshots, full history retention, so any corrupted upload can be rolled back to the last clean copy) be confirmed adequate before shipping — Chao confirmed the existing design already met this. Shipped to production 09/17/2024 for both the Diefootprint and Generalfootprint upload endpoints. **This is the direct precedent for the broader 02/04/2025 ask below** (Wingra asking to remove auth from the *search*/*advancesync* endpoints too) — Yu Han's answer differed there (redirected to OKTA/ID.Pass rather than granted), so don't conflate the two: upload-path header-based ID was accepted here, but a from-scratch request to drop auth on read/sync endpoints was not.

**Auth decision (02/04/2025)**: Wingra requested Jiapeng *remove* authentication entirely from IDI's search and advancesync API endpoints. Yu Han rejected that request and instead directed that authentication be added back — but via the OKTA-based ID.Pass token mechanism (see [[project-okta-sso-jwt-architecture]]) rather than NTLM, so engineers never type credentials directly. All "WRITE" operations (upload, adv-sync) must be authenticated and authorized; Jiapeng completed the change and deployed to staging. Why: a request to weaken security got redirected toward a more secure *and* more usable mechanism rather than simply declined or granted as-is.

**IDI auth pattern finalized (02/11/2025)**: IDI's web portal uses Cookie/OKTA auth; its `idi.data` S3 access API uses the ID.Pass token directly (issuer `brcm.wsd.swteam.idpass`) with **in-app ACL** authorization instead of the short-lived Access JWT — same pattern adopted for TAP (Phase 1). Separately, the DA team (Alex) asked IDI to instead support their own custom "DA-Token"; Yu Han declined in favor of the single ID.Pass mechanism — see [[feedback-engineering-principles]].

**Possible reversal, unconfirmed (02/18/2025, still the active direction as of 02/25/2025)**: the report states Chao synced with Alex and "agreed to support DA proposed option" (the custom DA-Token), which on its face contradicts Yu Han's 02/04/2025 rejection above. By 02/25/2025, "Chao and Alex aligned with new DA provided JWT Token method" and work was proceeding on that basis — so this is not a one-off remark, it's the direction actually being executed. Still not clear from the source whether Yu Han himself signed off on this reversal — flag and confirm current status before assuming either the ID.Pass-only principle or the DA-Token approach is Yu Han's actual intent.
