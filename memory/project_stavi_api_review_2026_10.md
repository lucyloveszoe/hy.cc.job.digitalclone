**What the doc defines:** `POST https://w6bk8mion5.execute-api.ap-southeast-1.amazonaws.com/stavi-query` (stage name is the path), body = JSON string holding a SQL SELECT. Four queries: `stproduct` (one column), `stwafer WHERE product IN` (filename, product, lotid, wafer, reader, processtime, eprocesstime, totalcount), `stwafersummary WHERE filename IN` (filename, category, qty, yield; cap 100 filenames), `stwaferdetail WHERE filename IN` (returns a URL list: `stwaferdetail_header.csv` then per-filename `.zip` on CloudFront `.../46/<file>.zip`; cap 100). Spotfire R data functions `zip_get_stproduct/stwafer/stwafersummary/stwaferdetail` in `wsd_share`, loaded with `source("https://atropos.s3-ap-southeast-1.amazonaws.com/spotfire/wsd_share.min.R")`; sample dashboard `/WSD_DEV/chao.sun/STMicro_test_2`.

**Findings:** (check first) SQL body with undocumented handling (injection or fragile grammar); no auth documented although Postman shows 9-10 headers; unsigned-looking predictable CloudFront URLs; unpinned remote R code from an apparently public S3 path. (docs) text shows `;` but screenshot body is a quoted string without it; no errors/limits behaviour; columns, time zone, category letters undocumented; `yield` is really category share (verified: 119/26717=0.004454, six rows sum to totalcount 26,717); detail zip format/link life/header-as-line-1 quirk; undated, personal-folder sample. (design) unbounded unpaged `stwafer`, ~2.7M detail rows possible at 100 files [verify], no freshness/discovery, no version, CSV-only.
