Originated 11/15/2023 from David (R&D)'s request: Ricardo and other R&D engineers wanted web-accessible R&D bench-test data (analysis/plots/reports/dashboards). Yu Han's early framing: no need for a separate "W platform" — simply hook TAP output into the existing zDB collection channel (30-min latency) or Real-Time Streaming channel (<5-min latency). By 01/16/2024 scope expanded to also cover Extractor FCM bench-test data (Penang FCM1-4 on TAP platform, FCM5 on C#). Held Jan-June 2024 pending Mitchell's team's parallel evaluation of an alternative NI database/analytics solution; officially unblocked 06/04/2024 when David/Ricardo/Mitchell confirmed moving forward, with David suggesting Early-2025 as the full-integration target.

**Yu Han's proposed rough schedule (06/12/2024)**: Late-June→Mid-July 2024 = catch-up on prior TAP technical research (Chao+Jiapeng, 20% BW); Mid-July→Late-Aug 2024 = finalize platform/tool selection + SOW/SRS (40% BW); Late-Aug→Late-Oct 2024 = Phase 1 (data collection + file-based access, 8 WW, 50% BW); Late-Oct 2024→Early-March 2025 = Phase 2 "parse+query" pipeline + full integration (20-24 WW, 50% BW, plus KinLum/Tingyu/Ken ~40% BW); Early-March→Late-May 2025 = post-integration high-priority support window (10 WW).

**Phase 1: Data Collection & File Access (Chao/Jiapeng/KinLum), target 10/25/2024**: reuses IDI's architecture (see [[project-wsd-logistics-data-integrity]]) migrated into the TAP domain — a Plug-In, full Web-Form, and low-level Web API (Upload/Download/Search/Tag). Two environments recognized: Lab Network (no internet, no direct S3 access, but reaches BRCM DC) vs. Personal Desktop/Laptop (internet access, direct S3 upload/download). Data types in scope: TAP results, S-Parameter/SNP files (very large — up to 1.9GB zipped / 3.5GB unzipped per single PID), FlatGD, Parametric Excel, Telecaster data. Stakeholders: David/Ricardo/Kushan (R&D), Mitchell/Gray/Eric/Xiaomiao (FCM/TAP dev team). Milestones: 07/25/2024 David surveyed the TAP user community; 08/01/2024 Round-1 review session held with FCM team, TAP dev team, and R&D testing team — team approved kicking off Phase 1; 08/06/2024 SRS in preparation. Volume stats collected: max single test run 32GB, max daily data 35GB, normal daily ~1GB per bench.

**Phase 2: TUDAS — the "SuperAnalyzer Engine" (Chao/Jiapeng/KinLum/Tingyu/Ken), target 03/21/2025**: this is the origin of the **TUDAS** platform name. Goal: SW team builds core/generic parsing+calculation algorithms plus a flexible Workflow Designer; qualified R&D domain experts compose custom Algos as a Workflow; a SuperAnalyzer Engine executes the custom Workflow and returns a free-schema, multi-entity result set decided by the Algo/Workflow designer (not a fixed schema). Followed by a 10 WW high-priority support window targeted 05/30/2025.

**SRS passed stakeholder review (08/29/2024)**: the PPT-form SRS was shared with and passed review by stakeholders, following the 08/01/2024 Round-1 kickoff approval — a concrete gate cleared ahead of the 10/25/2024 Phase 1 release target.

**Backbone architecture decision: DocumentDB + Aurora split, not a single store (09/03-09/17/2024)**: Kin Lum confirmed a single 16MB JSON document (DocumentDB/MongoDB's hard limit) is NOT big enough to hold a full TAP session's data (results + supplemental), even after applying data encoding to shrink it. Decision: use **DocumentDB** to hold "Result" meta (same pattern as zDB Types 15/19), and **Aurora** to hold "Supplemental" data (same pattern as Type 13), linked by a shared **Test_Session_ID** primary key. DocumentDB cluster stood up via IaC in AWS Oregon for dev/test (`WSD.TF` `wsd-tap/aws/WSD.Tap/main.tf`, later moved to a dedicated VPC under `WSD.Tap.v2` — see below).

**AppRunner/DocumentDB private-subnet blocker, resolved (09/03-09/17/2024)**: AppRunner requires deployment in a private subnet; DocumentDB is also recommended in a private subnet; but WSD's BRCM-VPN-whitelisted VPC CIDR only had 2 *public* subnets, no private ones, so AppRunner couldn't be created in the same VPC as DocumentDB. Kin Lum requested additional private-subnet CIDR from BRCM IT (Dean); **Dean approved 3 new private CIDRs (Tokyo, Oregon, Singapore) by 09/17/2024**, and the team set up a dedicated VPC for DocumentDB (`WSD.Tap.v2`) to deploy both services together as originally intended — resolved, not a lingering blocker.

**Phase 1 (Data Collection & File Access) released 10/29/2024** — 4 days after its 10/25/2024 target, officially marked Complete. Confirms this phase actually shipped rather than remaining an open SRS-prep item as of the 08/06/2024 status previously recorded. **Post-release deployment support marked complete 12/02/2024** with no pending issues/requests — TAP dev team confirmed their own working development version, UI finalization still theirs to do, nothing released to their own customers yet.

**Phase 2 design-consolidation gated on real-world data volume, not just stakeholder agreement**: talks with stakeholders (Chung Sik, Mohamed, Ricardo, David, Mitchell) to agree on TUDAS's advanced-query strategy ran through Nov-Dec 2024 without full agreement — David's framing (11/19/2024): "TAP is fundamentally designed for flexibility... it's difficult to categorize the types of tests." SW team set a fallback: if no agreement by 12/02/2024, proceed with the MUST-DO minimum of cloning WUDAS into the TAP domain. In parallel, Yu Han set a **Phase 2 Design Consolidation date of mid-January 2025**, gated on collecting 200+ real-world TAP session records as the design/justification base (David: install the collector on more benches) — by 12/23/2024 only **40+ sessions** had been collected, well short of the 200 target, so Phase 2 scope work continued without the full data set.

**TUDAS full name and positioning clarified (02/11/2025)**: TUDAS = **TAP Unified Data Access Service** — explicitly framed as the R&D counterpart to **WUDAS** (WSD Unified Data Access Service) in Production, i.e. the same unified-query-layer pattern applied to the R&D-bench-test domain instead of the manufacturing-test domain. Target date confirmed **07/29/2025**.

**Phase 2 data-collection target finally cleared (01/07/2025)**: the 200+ real-world-session collection goal (still short at 40+ as of 12/23/2024) was reported met by 01/07/2025 ("Real World TAP sessions data sets collected"), clearing the gate for full Phase 2 design work to start. **Collector 1.1.3 released 01/14/2025** (Tingyu) — fixed a bug where overlong TAP file paths failed collection. **Stats as of 02/10/2025**: 14 benches deployed, 1,113 data sets collected total (79 from trace testing), SNP files up to 9,838 per set, ~27GB total volume — a large jump past the original 200-session bar, now tracked by volume/bench-count rather than just session count.

**Phase 2 design underway, architecture question raised (01/07-02/11/2025)**: Chao/Jiapeng started high-level design on TAP result parsed-data output format; SOW/Phase-II doc shared with PE's Chung Sik, who wants R&D to use the TUDAS Phase II query to pull SNP data for dashboards. Design output targeted **WW10 (~03/2025)**. Open architecture question raised internally: given WUDAS's own history of eventually unifying Cleada/zDB-ODBC into one fully task-based query style after early growing pains, should TUDAS be designed as fully task-based from the start rather than repeating that same "early-stage vs. task-based" transition later? Gray (stakeholder) recommended the open-source `scikit-rf` library for SNP file parsing/plotting. Benchmark POC datasets defined: small (50MB×1000 files), medium (6GB×200), large (26.5GB×20).

**Phase 2 POC design settled and shipped for its first use case (03/10-04/08/2025)**: TUDAS launched a live web portal at `https://tudas.broadcom.net/` (POC hosted at port 9000). Architecture: all query use cases share a common Step 1 (get header, ~4s) and Step 2 (get row, ~50s), differing only in Step 3 (data processing). **Use Case #1 "SNP Data Stitch"** — the pilot/POC use case — reached **Complete** by 04/08/2025: 3 UI entry points (tag-based stitching, one-time query, and a "Query Pool" that stores/replays all past queries), with a SNP-stitching worker (Jiapeng) that beat its 1-hour performance goal by a wide margin (worst case 9,612 SNP files / 27GB → 4.2GB stitched CSV in ~10 min). Demoed to SJ stakeholders (David/Mitchell) 03/21/2025 with positive feedback; Chung Sik separately wants to point his R&D dashboard at this API. **Use Case #2 "TAP Worst Case Parameter Search"** — in progress as of 04/08/2025 (workflow: tag TAP results, define specs with param/set conditions, a Cleada worker computes worst-case Min/Max/Avg/Med/Std per spec, results to S3). **Use Case #3 "Supplemental File Access"** — mostly complete (web/cloud-engine controllers done; deploying via Cleada since AppRunner doesn't support mountable storage). **Use Case #4 "TAP Result Full Range Data Stats"** — not started. Data collection kept scaling through this period on the same 18-20 deployed benches: ~1,113 data sets (02/10) → 1,818 (02/25) → 2,200 (03/04) → 2,485 (03/10) → 2,939 (03/18), ~27GB total — track the live tracking sheet (linked in weekly reports) rather than any single snapshot number here.

**Phase 2 backbone architecture and infra decisions (04/22-06/03/2025)**: TUDAS is being built as a full backbone API set (explicitly "just like GCP" — same single-source-of-APIs pattern as [[project-gcp-api-umbrella]]) serving multiple front-end clients — the TUDAS Web Portal (SW team's own focus for the 07/29/2025 round), a Spotfire Dashboard (Chung Sik's parallel workstream), and FCM Analyzer (explicitly deferred to a separate follow-on integration project once the backbone proves out against the Web Portal/Spotfire). All other clients must write custom scripting against the TUDAS API directly. Concrete API surface taking shape: a Common Result File API (get all PC names, search by metadata/Cid, get headers), a TUDAS Task API (check status, download result), UC#1's SNP-stitch endpoints, and UC#4's raw-result-stitch endpoint — UC#2 (Worst Case Study) and UC#3 (Supplement Zip) APIs still "TBD." Infra: Jenkins pipeline for feeders and Cleada TAP autoscaling (dev environment) both reached Complete; Jenkins pipeline for workers still in progress; long-term deployment choice between a CLEADA Cluster and ECS is due by 06/16/2025 (Chao).

**Use Case #1 entering wrap-up, #2/#3 continuing (04/22-06/03/2025)**: UC#1 "SNP Data Stitch" moved from "Complete" to "(Wrap-up)" status — no new functional work, just closing out. UC#2 "TAP Worst Case Parameter Search": workflow/UI design fully spec'd (tag-based spec configuration, Cleada worker computes Min/Max/Avg/Med/Std per spec, results to S3), breakdown/assignment in progress. UC#3 "Supplemental File Access": web/cloud-engine controllers complete; deployment blocked on AppRunner's lack of mountable storage, so the team is evaluating Cleada (picked a C5.xlarge Linux EC2 with IO2 32000 IOPS, ~32s/GB, already beating its performance goal) pending an ECS-option comparison before finalizing.

**Phase 2 marked COMPLETE on its 07/29/2025 target (reported ww30)** — closes out the entire "zDB expansion to cover R&D Bench TAP Testing Phase 2: TUDAS" project. Final use-case roster (renumbered from the 04/22-06/03/2025 snapshot above — a new UC4 was inserted, pushing the old UC4 to UC5, which was then dropped):
- **UC#1 "SNP Data Stitch"**: Done (already recorded above).
- **UC#2 "TAP Worst Case Parameter Search"**: Done — Cleada worker computes worst-case Min/Max/Avg/Med/Std per spec from a tag-based condition/result dataset pairing; positive demo feedback from Mitch's team; future consideration noted (not yet built) to auto-translate Raptor's official spec files into TUDAS JSON input, possibly via Turker's existing utility or FCM Analyzer.
- **UC#3 "Supplemental File Access"**: Done — deployed on Cleada (C5.xlarge Linux EC2, IO2 32000 IOPS), ~32s/GB, beat its performance goal (AppRunner ruled out — no mountable/configurable storage support).
- **UC#4 "TAP Result Stitch"** (new use case, not in the earlier 4-UC snapshot) — Done: stitches multiple TAP result files into one dataset (Chung Sik's request); measured performance 20 files/46MB → 2.37s, 1000 files/4GB → 29.3s after optimization (async I/O, in-memory instead of disk, migrated to CLEADA-style structure).
- **UC#5 "TAP Result Full Range Data Stats"** (renumbered from the earlier UC#4) — **dropped from the 07/29 cycle**, per Chao: "scope and ROI are fuzzy." If this use case resurfaces, treat it as unbuilt, not deprioritized-but-planned.

**TAP data collection region-routing decision (07/29/2025)**: evaluated 3 options (all-sites-to-SJ-share-folder vs. direct-per-tester upload vs. SW-deployed collector per site) and **decided to keep the AS-IS approach** — all regions route TAP data to the San Jose FTP share folder (`scm01.sjs.broadcom.net`, `C:\Broadcom\TapToZdb.Ftp`, confirmed >100GB capacity) — trading network bandwidth/share-folder size for reusing the same installer everywhere, rather than building per-tester upload APIs or deploying dedicated collectors at each site. As of this date: San Jose fully covered, MUC sending data to San Jose, Penang still on an older FlexTest TAP package version that predates TUDAS integration (will auto-pick-up TUDAS once they update), no known Seoul usage.

**Penang/MUC TAP collection to SJ share folder — enabled (completed, reported ww31+32 08/12/2025)**: executing the "AS-IS" region-routing decision above required a new firewall exception (ticket FM2597200) — Penang's/MUC's FTP access to the SJ share-folder server (`scm01.sjs.broadcom.net`) was blocked by default; WSD requested and got FTP access granted from Penang's office/lab/WiFi subnets (10.93.x.x ranges) and MUC. Treat all-region TAP-to-SJ collection as now actually working, not just decided.

**TUDAS Usage Report shipped; broader "expand TUDAS user base" investigation still open (09/17-09/26/2025)**: per a 09/16/2025 Chao/Jiapeng/Ken discussion, Ken drafted an "expand TUDAS user base" proposal covering (a) a flexible ad-hoc charting front-end directly on the TUDAS API (vs. today's two-step "call API, then find a charting tool" workflow) with potential coverage of SJ NPI Clotho ATE data, TAP data (SJ+Penang), and Seoul FCM Clotho ATE data; (b) evaluating whether to instead just promote Spotfire as that ad-hoc charting front-end for expert users; and (c) a TUDAS Usage Report to justify any expansion investment. Ken shipped just the Usage Report (Complete, ~09/26/2025) — usage still low, plan to share with the external TUDAS-users PDL once monthly task-count or raw-data volume exceeds 1TB. By 10/07/2025 Ken had an initial SOW/SRS draft for the charting-front-end idea (consolidate Clotho ATE results — header + system columns + GD-broken-down parameter columns — into a fixed-column sparse CSV, compared against both Spotfire and PADMA), but goals/target-user-groups were still pending clarification — treat the charting-front-end piece as unresolved, only the Usage Report as shipped.

**TUDAS Intro/Demo session run for SJ R&D, with a first adoption milestone goal set (11/10-11/21/2025)**: per Ricardo's suggestion, Ken ran an onboarding/demo session (11/21/2025) for SJ R&D, covering feedback collection, bug reporting, and new-feature requests, and onboarded all attendees with TUDAS access (Web Portal user manual and API introduction docs published). As of Nov 2025, actual utilization was still tiny — 6 users, <300 task requests total. **First adoption milestone set**: by 06/01/2026, beat >40 active users and >120,000 task requests/month — a concrete target to check TUDAS adoption against going forward, distinct from the "expand TUDAS user base" investigation (charting front-end idea) tracked above.

**Penang Spotfire/TUDAS integration scaling fix (completed 11/25/2025)**: Kenny (Penang) needed to pull TUDAS "attr" (DUT attribute) data into Spotfire via the `gettapresultstitch` query, but large queries were returning limited rows or failing outright. Root cause: the parser reused the low-volume PCB-Cu setup and choked on a 1.02M-row result. Tingyu fixed it by upgrading the parsing core from Lambda to ECS (16GB memory) and switching the compute-sizing decision logic from "CID count" to "CID data size." Marked complete as a short-term fix; a smarter, dynamically-sized ECS container allocation and workload-balancer logic rewrite were deferred to the next major WUDAS/TUDAS upgrade cycle.

**Silent Penang data-collection gap incident, response still "In Plan" as of 12/09/2025**: Kenny reported (11/03/2025) that TAP data from Penang's FCM testers had silently stopped uploading since 08/29/2025 — over 2 months undetected. Beyond the CAT team's own bug fix, Tingyu is planning a **TUDAS Data Collection Health Monitoring and Failure Reporting Service** to catch this class of long, silent collection gap going forward (e.g. from IT failures). As of 12/09/2025 status was just "plan to create a data collection monitor" — no design/target date yet, and the item stopped appearing in weekly reports after that date without a recorded resolution; treat as an open, unstaffed-in-detail gap rather than assuming it shipped.
