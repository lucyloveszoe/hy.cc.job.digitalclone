FCM Analyzer (owned mainly by Chao/Jiapeng/Tingyu, with Ken) has several parallel workstreams active as of ww34 (08/25/2026), following on from FCM Analyzer V1.1.0's production release (see [[project-gd-breakdown-flexplot]] for the FCM-Telecaster-I / V1.1.0 history).

**Earliest confirmed active use predates both of those: 08/06/2024.** Per Mitchell's request, Chao/Jiapeng demoed FCM Analyzer against real Buster Dev2 TAP data (flatGD format, ~2GB/PID) and a real spec (`Buster_UHB_EPT_PAD_Specification`), with Mitchell sharing a long-term ambition even then to search the database by Spec_ID/Spec-number and compare across product phases/products. This ties to the same TAP/FCM data source as [[project-rd-bench-tap-testing-tudas-origin]] — treat that project as FCM Analyzer's data-pipeline sibling, not an unrelated initiative.

**Demo completed with positive feedback, wrapped up (08/15/2024)**: after an internal demo (08/09) and bug fixes/testing at ~240K-row scale, Chao/Jiapeng ran the full demo for San Jose's TAP (David) and FCM (Mitchell/Gray) teams — positive feedback, well aligned with FCM's existing Worst-Case-Study practice. Team explicitly expects a "big upgrade" once (a) Raptor defines a standard Spec format and (b) the TAP+zDB Phase 1/Phase 2 pipeline ([[project-rd-bench-tap-testing-tudas-origin]]) lands — i.e. this demo previews FCM Analyzer's eventual TUDAS-integration path, not a standalone deliverable. Since no further near-term development was planned at that scope, the item was marked Complete as of this demo rather than left open-ended.

As of 08/25/2026, still in requirement clarification with Mitchell's team; Mitchell asked (08/28/2026) for histogram charts in time for Oct/Proto-2, calling basic histograms very helpful for data review/debugging even before the larger outlier-removal upgrade lands. Yu Han's initial rough investment estimate: an API gateway plus a new TUDAS backbone handler on sufficiently high-spec hardware.

**Telecaster-II: Enable Full Automated Workflow (Chao/Tingyu/Jiapeng, In Plan)**: Mitchell and Yu Han synced 07/29/2026 — SW team is fully committed to giving the FCM team needed features on demand. A 08/11/2026 sync with Mitchell's team clarified requirements: (1) a user-definable-formula calculation engine, since the underlying calculations change often and the team wants to stop depending on SW to hard-code formulas (to be discussed further in a dedicated brainstorming session); (2) a simple box-type distribution plot to quickly spot outliers/bimodal distributions during data review. Note: an earlier iteration of Telecaster work was flagged in [[feedback-engineering-principles]] as one of several "urgent" requests (FCM Analyzer Outlier Removal, FCM-Telecaster-II, worst-case-snp) that went unused after being rushed through — factor that history in before fast-tracking new Telecaster-II asks.

**NXG FCM Analyzer & TUDAS Expansion to TAP and ATE Formats — origin (07/14/2025)**: kicked off as "NXG FCM Analyzer Upgrade" (Chao/Jiapeng) per Mitchell's proposal, initial sync held 07/14/2025, no target date set at kickoff. Framed then as: SW team builds the new FCM data pipeline to ease FCM's day-to-day workload while keeping standard charting covered, plus full support for Spotfire FCM Data Function needs. This is the direct origin of the 3-phase plan described next (the 08/25/2025 status snapshot below is ~6 weeks after this kickoff, not the start).

**NXG FCM Analyzer & TUDAS Expansion to TAP and ATE Formats (Chao/Jiapeng/Tingyu/Ken, Hold)**: a 3-phase plan — **FCM-TAP** (expand FCM Analyzer so all Telecaster-built functions also work for SJ's TAP format; main work is an automated `Filter.json` to align TAP's different header keywords with Telecaster's); **TUDAS-EX2** (expand TUDAS data collection to Seoul ATE result data, new parsers, possible TUDAS DB adjustment); **FCM-ATE** (extend Telecaster+TAP functions to Seoul ATE format, plus new features: publish results to Raptor Spectre format, continued SJ FCM Google-Sheet support, auto-generated comparison slides across Spec/Product revisions). Two rollout phases discussed with Mitchell: Phase I keeps existing G-Sheets but adds FCM Analyzer integration with the Turker Spec Portal + TUDAS backbone for auto filter/align/stitch by customer spec ID; Phase II drops G-Sheets entirely in favor of a dedicated WSD FCM Web Portal (PPYCC-style single-source-of-truth DB, with Excel import/export and per-spec comment/collaboration tracking) — FCM Analyzer would remain the front-end computation interface, writing results into the FCM DB which propagates to the Portal. Status as of 08/25/2025 (per report): Kenny confirmed Penang will migrate to full TAP coverage; by 09/02/2025, 47 TAP testers were covered (2 MUC, 8 Penang, 37 SJ) with 327 Penang datasets collected since 08/01 and randomly-spot-checked parsing confirmed working; most recent roadmap sync was Mitchell/Chao on 11/13/2025 — no more recent update recorded, so this workstream may be stale relative to ww34 despite being listed as currently Hold rather than closed.

**FCM-Analyzer Utility: Sunset Plan (In Plan, owner TBD)**: long-term direction (shared with the FCM team 08/18/2026, based on Mitchell's Spotfire support request) is to drop or minimize SW-team support for "limited user base" desktop applications/utility front-ends, on the assumption that either (1) domain experts self-serve quick prototypes via Claude Code (as already observed in Design/Production/NPI teams), or (2) FCM Analyzer's functions get consolidated into the central TUDAS Portal or Spotfire Dashboard instead. SW team's stated redirection of investment: more into shared middleware/centralized portals (TUDAS Portal, WUDAS APIs, pCD U-Portal, Spotfire Data Functions) and core backbone (cloud-based large-scale data access/computation), less into one-off desktop utilities — explicitly a long-term direction, not an immediate change to current support practices. This is the same direction already captured as a general principle in [[feedback-engineering-principles]] ("don't maintain one-off internal front-ends long-term").

**Why:** FCM Analyzer is WSD's primary tool bridging FCM/RF characterization data into TUDAS, so its several parallel expansion/automation workstreams and its own eventual sunset plan are all part of one program even though tracked as separate report line items.

**How to apply:** update each workstream's status independently as it progresses — they have different owners, targets, and paces. Don't fast-track Telecaster-II-style "urgent" asks without checking actual usage first, per the linked feedback principle.
