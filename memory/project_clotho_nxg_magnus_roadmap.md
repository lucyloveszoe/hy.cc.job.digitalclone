2024 continuation of the team's recurring "next-gen Clotho" ambition — the same lineage as 2023's "Project Hydra" vision (see [[project-2023-annual-review]]) and a likely ancestor of the 2026 NXG platform work in [[project-nxg-pipeline-and-raptor]], though no document explicitly links all three.

**DEC2 (Domain/Distributed Edge Computation Cluster) investigation (Jan-Feb 2024)**: explored building a Kafka-based real-time streaming/plug-in processing layer on top of existing pCD+zDB+Handler+TestPlan architecture (backward compatible, no change to existing tester drive sequence). Benchmarked AWS MSK (managed Kafka) extensively — confirmed low/medium-spec brokers handle small (~1KB) message workloads fine, but large (10MB) messages hit throughput bottlenecks requiring multiple producers/partitions. Consolidated the community's 28-item Clotho enhancement wishlist (originally collected 12/08/2023) into 3 groups (02/02/2024, YK/Yu Han/Kin Lum sync): **Group 1** = requires re-architecture → marked "NXG V1.0"; **Group 2** = real-time comm protocol addable to existing Clotho → marked "Clotho V5.x" (MQTT already used by TDG but capped at small-volume RTS, insufficient for mid/long-term goals); **Group 3** = high-ROI items fitting current architecture → "Clotho 4.x" upgrade cycle.

**KP decision (02/07/2024) — custom on-prem CM Kafka deployment put on hold**: KP judged in-CM custom Kafka technically/operationally too heavy given HA/DR requirements and the team's existing workload, and directed the team to pursue MQTT-based CM migration (Clotho v5.x) plus misc Clotho v4.x upgrades instead, while KP separately evaluates industry "buy" vs. "build" options. Hold this DEC2/Kafka-in-CM discussion until a buy option is ruled out. **Gen-QS** (the AWS-MSK-hosted managed-Kafka backbone-simplification project, distinct from in-CM Kafka) was NOT put on hold — it continued as KP-approved (target 04/26/2024) and reached production-usable state through 2024: both Public/Private MSK access points set up, Kadeck adopted as the MSK monitoring UI, and a hybrid access-pattern decision made for CM/BRCM-domain clients (API Gateway + Lambda + Private AP, chosen over a REST proxy or ALB for universality) since raw Kafka ports (909x, then attempted custom-port remap to 80/443) aren't reachable from CM/BRCM domains.

**"Magnus" + pCD-IV investigation (Apr-Jun 2024)**: **Magnus is the internal codename for NXG Clotho.** Two internal brainstorming sessions held (04/16 and 05/17/2024) to define goals/approach and align on what "modularized" production/expert-cal test code means, cross-referencing Penang TDG's own modular-code documentation and a 13-year-old prior-company homegrown test platform (configurable web UI, modular test cases, visualization, algorithm configs) as an aspirational reference point. **Stalled 06/05/2024** — explicitly deprioritized due to competing new-request pressure, with no further progress recorded through year-end 2024.

**SW Team 3-Year Roadmap (draft 12/23/2024, reported ww01/2025)**: YK/JJ proposed a Clotho/pCD 3-year roadmap aligned to the product release cycle, with major releases timed between Proto stage and EVT stage. Draft timeline: **Clotho 6.0 (or 6.X) targeted 2025.11**; **pCD-IV + Clotho 7.0 (NXG) targeted 2026.11**. A required decision, no later than 2025.04, on whether Wafer testing code is 100% absorbed into Clotho or 0% isolated from it — still pending management decision as of 01/07/2025 (per a 12/17/2024 sync between Yu Han/YK/Kin Lum and PE's Chung Sik/Kuok Liang and TDG's JJ/Chor Ming/Kuok Liang). Kuok Liang's input: wafer-sort work is mostly regen/post-processing so doesn't need much of Clotho's backend feature set, while pCD's main (PE) users mainly need quick/simple deployment — a genuinely different use case from backend testing. Separately, per a KP request, testing-irrelevant code is being split out of the TDG codebase (tracked in the same 28-item Clotho feature sheet as the DEC2/Magnus work above). See [[project-pcd-clotho-v7]] for the 2026 resolution of this Wafer-vs-Clotho scope question.

**Wafer-vs-Clotho decision narrows to two concrete proposals (04/10/2025)**: continuing the restarted Chung Sik sync (04/08/2025 above), the "no later than 2025.04" decision deadline from the 3-year roadmap now has two explicit options on the table. **Proposal #1** — completely absorb Wafer Probe testing into (NXG) Clotho: upgrade Clotho's current single-level `Load→SOT→EOT→...→Unload` driving logic to a dual-level `Load→SOT→Scan1→Scan2→...→ScanM→EOT→Unload` model covering both Module and Wafer testing, absorb the Wafer Prober UI into Clotho, auto-enable pCD/zDB/DPAT interfaces for both test types, make Kuok Liang (TDG) a co-owner of NXG Clotho, and take the opportunity to upgrade NXG Clotho to .NET 10 for performance. **Proposal #2** — evolve pCD from its current semi-automatic (pCD-III) release process to a full CI/CD pCD-IV: package releases triggered by a GitHub pull request to a "deploy" branch, with minimal (changed-files-only) distribution artifacts — well-suited to Wafer Prober's needs — replacing manual pCD releases with GitHub PR review, developed jointly with PE to define the wafer package structure. No decision made yet as of this report; still pending management call.

**Site-2-Site technical direction: gRPC ruled out, MQTT confirmed viable (04/15/2025)**: as part of the Clotho V5.3/Site-2-Site Communication investigation (sequenced after WAFERSORT.BSIRREGEN and OKTA/Dual-JWT, both now complete — see above), the team found **gRPC does not work well on .NET Framework** (limited HTTP/2 support, no ASP.NET Core hosting for gRPC-Web) and a full .NET-Core/8/10 migration is currently blocked by test-hardware driver compatibility (drivers only support .NET Framework 4 for the foreseeable future). Experiments confirmed **RPC-style communication emulated over MQTT works on .NET Framework** — MQTT is therefore the working technical direction for Site-2-Site, not gRPC.

**TDG .NET-platform roadmap debate, unresolved (04/15/2025)**: TDG (Module & Wafer team, per JJ) prefers to stay on **.NET Framework** rather than move to modern .NET, citing hardware-driver dependency risk — NI and Keysight will only support .NET 8/9 (compatible with .NET 10) drivers by end of 2026, and JJ worries that if new vendor drivers break Clotho's current interface/code structure, it could stall the migration and leave Clotho's .NET-Framework line unsupportable for bug fixes during any transition. JJ's ask: guaranteed **dual-platform (.NET Framework Clotho + .NET Clotho) bug-fix/critical-update support** during any transition period. Yu Han's counter-position: NXG Clotho should target **.NET 8 or .NET 10** for its materially faster runtime, will remain a modularized Windows desktop app with the same Test Plan interface (so most test-plan code should need only a recompile, "days not weeks/months" of migration effort for console/class-library-style code), and can simply align its release schedule with equipment vendors' driver release timelines rather than being blocked by them; a Linux-OS option also exists for PXI controllers from both NI and Keysight if needed. **Pending further clarification with JJ** — no resolution yet; track before assuming NXG Clotho's target framework is settled.

**Wafer-vs-Clotho decision AND the TDG .NET-platform debate both administratively closed and merged into one consolidated roadmap item (04/29/2025)**: rather than resolving either open question, the team closed both standalone threads ("Clotho NXG + pCD IV vs. Wafer Clarification" and "Support TDG Module & Wafer Test Software .NET Platform Roadmap") and folded them into a single renamed tracking item, **"pCD-IV/NXG-Clotho/Wafer 3-Years Roadmap"** (YK/KinLum/Chao/Choo-yau/Jiapeng), now listing three concrete action items with no decision made yet on any of them: **(1)** upgrade NXG Clotho to .NET 8/9/10 — next step is a head-to-head performance demo of .NET 8/9/10 vs. .NET Framework 4 on the *existing* (non-NXG) Clotho codebase, plus a feasibility POC for a Linux migration if financially/operationally viable; **(2)** completely absorb Wafer Probe into NXG Clotho (the former Proposal #1 — dual-level test driving logic, Wafer Prober UI absorbed, Kuok Liang as NXG-Clotho co-owner); **(3)** evolve pCD-III to a full CI/CD pCD-IV (the former Proposal #2 — GitHub-PR-triggered minimal-diff releases). Explicitly still **pending further input from Chung Sik** — treat the underlying wafer-vs-Clotho and .NET-platform questions as still open, just tracked under this new consolidated name going forward.

**Wafer-vs-Clotho question graduates into a formal standalone project, "pCD-IV/Wafer/Clotho Design" (05/05-05/13/2025)**: the consolidated roadmap thread (above) closed and was promoted into its own project, owned by the SW team, **target date 07/31/2025** (deliverable: a full-scope SOW + optional SRS design doc). This followed a 05/05/2025 sync with PE's Chung Sik/Kuok Liang and other Penang wafer experts that produced real technical substance, not just proposals: **current landscape** — pCD is deployed only at Chipbond and Sawnics; **Inari has not adopted pCD due to a 64-bit gap**; pCD-III has "show-stopper" gaps because spec-limit files change frequently while test plans change rarely, and WSD needs one Test Plan usable across all projects. **Draft pCD-IV ideas**: a lookup table (spec-name → specific spec-limit-file version, keyed by GitHub tag), Jenkins CI/CD driven by `git pull <specific_tag>`, defaulting to the latest revision when a spec-name isn't explicitly listed, and enforcing the same revision across 1st Probe/2nd Probe/H2 via either central MySQL or a GitHub batch tag. **Key feasibility finding**: there is no direct hand-shake between the test-plan domain and the handler domain today — all SOT/EOT control flows through the Clotho Engine for wafer exactly as it does for module testing — so merging wafer logic into Clotho does **not** require any change to the tester drive sequence, which was the main migration-risk concern. **Draft pCD-IV scope**: a backbone (Git workflow, Jenkins CI/CD, lookup-table-driven special-logic hooks, a wafer-probe portal, auto-generated spec files from templates) plus optional components (a DB-oriented wafer-only UI similar to PPYCC, a lightweight pCD client wrapping Git operations). Plan: extract wafer-specific libraries into Clotho while keeping them persistent, and maintain full backward compatibility for the existing Chipbond/Sawnics deployments if possible. As of 05/13/2025: "initial agreements from all stakeholders," now being consolidated into the formal Design doc — track this as the authoritative continuation of the Wafer-vs-Clotho and pCD-IV threads above.
