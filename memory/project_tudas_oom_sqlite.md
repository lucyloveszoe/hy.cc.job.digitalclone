TUDAS had a recurring out-of-memory / memory-spike issue when parsing large JSON files (tied to a past system-down incident). The team evaluated MemoryMappedFile vs. per-file SQLite and chose SQLite despite MemoryMappedFile testing better in raw performance, prioritizing long-term architectural fit for parsing (see [[feedback-engineering-principles]] on decision criteria) — specifically, TUDAS requires ongoing byte-array updates during parsing, unlike WUDAS's write-once/read-only pattern, which SQLite fits better. Design: 1 TUDAS file → 1 SQLite DB, with `data`/`row` tables.

Chao began implementing the feeder-code change (write SQLite instead of JSON) starting around ww15-17 (Apr 2026) — so implementation is in progress even though full rollout is still described as held for the next NXG TUDAS upgrade cycle.

**Why:** a real reliability incident drove this, and the fix is deliberately bundled into a larger planned upgrade.

**How to apply:** treat this as resolved-in-design, in-progress-in-implementation; update when the NXG TUDAS upgrade (and this migration within it) actually ships to production.

**Earlier origin — TUDAS Phase 2 Advanced Data Query scoping (Jan 2025)**: this OOM/SQLite issue surfaced during implementation of a TUDAS capability first scoped a year earlier. "zDB expansion to cover R&D Bench TAP Testing Phase 2: TUDAS" began as an advanced-data-query project (query TAP result data beyond simple lot/file lookup), separate from the OOM bug above. As of 01/14/2025, ~200+ real-world TAP session datasets had been collected as the design basis, and the team (Chao/Jiapeng) split the scope into **Phase 2-A** ("SNP" extended filename+header+content search) and **Phase 2-B** (the remaining 3 use cases), pending SOW/SRS and an estimated 4-engineer schedule.

**TUDAS target date and POC (02/11/2025)**: TUDAS is framed as the R&D counterpart to WUDAS — a "search-and-stitch" web API service for R&D TAP/FCM teams, aiming to cut analysis time from days/weeks to hours/minutes via a single source of truth integrated with Spotfire/JMP/MATLAB. Target date set to **07/29/2025**, with a POC phase to pick a "winning" design by WW10 (~early March 2025). Data collection scaled to 14 benches / 1,113 datasets (~27GB of SNP files); Tingyu built small/medium/large synthetic benchmark datasets (50MBx1000, 6GBx200, 26.5GBx20) for POC performance testing.

**POC progress (03/04/2025)**: data collection grew to **20 benches, 2,200 datasets, 136 trace sessions, max 9,838 SNP files, ~27GB total**. SRS document for TUDAS Phase 2 drafted and pending stakeholder review; Chao/Jiapeng completed the TAP query-request-format brainstorming and a test program to parse SNP files; SNP-stitch and TAP-detail-row-stitch functions in development. A supplemental-data-access constraint surfaced: AWS App Runner (the hosting layer) provides no configurable/mountable storage, so large-volume queries (~7MB/file x1000 files = 7GB) take ~20 min vs. <2 min for small-volume queries — a performance factor to account for before the WW10 "winning design" decision. Chung-Sik's R&D dashboard demo showed a preference for querying TUDAS Phase 2 directly for SNP data rather than an alternative path, and he intends to push R&D toward TUDAS generally.

**WW10 "winning design" milestone hit on schedule (03/10/2025)**: data collection reached **2,485 datasets** across the same 20 benches. Stakeholders (Chun Hao, Chung Sik) bought off the SRS. The SNP Data Stitching worker (Jiapeng, deployed on EC2) beat its performance goal — worst case (9,612 SNP files, 27GB total, 4.2GB stitched CSV output) completed in **~10 minutes vs. the 1-hour target**. A 3-option query UI/workflow was clarified (one-time query from a file-search result list; direct query-type launch; re-run from a saved query-pool job), backed by real FCM-lab data loaded into a POC DocumentDB + new AppRunner instance. This SNP-stitching/EC2-worker/DocumentDB architecture is effectively the "winning design" the WW10 checkpoint was meant to select.

**Post-WW10 continued growth (03/18/2025)**: data collection continued growing past the winning-design checkpoint — same 20 benches now show **2,939 datasets, 231 trace sessions**, max 9,838 SNP files, ~27GB total — confirming data collection continues in parallel with the now-selected architecture moving into build-out.

**POC demoed to San Jose stakeholders with positive feedback (03/21/2025)**: Chao/Jiapeng/Tingyu/Ken/KinLum held a Phase-2 POC demo for the San Jose team; David and Mitch gave positive feedback on overall function and workflow. The POC web UI (SnpStitch page + QueryPool page, supporting query-from-history-conditions) is live at `tudas.broadcom.net:9000`. As of 03/25/2025 the team is still building out this UI and preparing real TAP data from Gray's SJ FCM-lab bench into the POC DocumentDB; a supplemental-data-access service (for large files like s8p/s9p) remains on hold until the POC is done, since AWS App Runner still provides no mountable storage for it.

**Concrete release schedule to the 07/29/2025 target confirmed (06/10/2025)**: 07/04 — draft code freeze, release full-suite trial versions, begin FCM-Analyzer-integration discussion with Mitchell's team; 07/20 — all stakeholders (TUDAS web portal + Spotfire dashboard) trial for 2 weeks with high-priority support from the team; 07/21 — final round of code polish; 07/29 — official release. Prod DB migration already completed as of this date.

**Infra architecture decision: ECS over EC2-autoscaling (06/17/2025)**: Ken ran a head-to-head comparison of TUDAS's CLEADA-style EC2 autoscaling (1-3 EC2, 4 tasks/EC2, avg 1 CPU/2GB per task) vs. ECS (0-12 tasks, 2 CPU/4GB per task) against a 90-task workload — ECS wins on processing time (double the spec) and cost (cheaper once average daily utilization is ~8 hours), while CLEADA only wins on cold-start when task count stays ≤4. **Yu Han decided to use ECS as the backbone infra** for TUDAS going forward (Tingyu/Ken own the ~3-week migration, targeting dev-done end of June, full completion first week of July). This also updates the release schedule slightly: 07/09 draft code freeze (was 07/04), 07/22 stakeholder trial begins (was 07/20), 07/23 final polish (was 07/21), 07/29 official release unchanged.

**Refined to a Lambda/ECS hybrid, not pure ECS (06/24/2025)**: the actual migration design splits by workload type rather than moving everything to ECS: **Lambda** for "Results"-related tasks (small/frequent files — fast cold start, cheaper, event-driven autoscaling) and **ECS** for "Supplemental"-related tasks (large/infrequent files — slower cold start, more expensive, custom-scheduler-driven autoscaling), with routing logic to send each request to the right backbone based on workload/feature. Benchmark: Lambda running a 1000-file result-stitch (~28.5s) performs about the same as EC2 c5.xlarge (29.3s). Treat "ECS as backbone" from the 06/17 entry above as superseded by this more precise hybrid design.

**Lambda/ECS hybrid migration essentially complete (07/08/2025)**: code refactored into one consolidated solution (all task handlers grouped together, config collapsed from 20+ files to 4), with `LambdaEntrypoint.cs`/`EcsEntrypoint.cs` entry points, dev/prod setup and testing done, and the Lambda-vs-ECS routing threshold tuned from real result/SNP/supplemental data. Only the ECS task-scheduler CI/CD/IaC piece remains in progress — everything else on this migration is done.

**"TUDAS Phase 2 Trial Release" announced, official release lands on schedule (07/10-07/29/2025)**: 07/10 — trial release announced with web-portal user manual and API documentation published; 07/14 — Chung Sik demoed the SpotFire/TUDAS integration (Spotfire itself doesn't support Smith-Chart plotting, but the team bridged this with on-demand Python-generated Smith-Chart images, static/non-interactive); 07/29 — **officially released**, exactly on the target date set back on 02/11/2025. Treat TUDAS Phase 2 (web portal + backbone API) as production-complete going forward.

**New sub-initiative: Data Collection Health Monitoring & Failure Reporting (11/13/2025, planning as of 12/02/2025)**: triggered by Kenny's 11/03/2025 report that TAP data from Penang FCM testers silently stopped uploading after 08/29/2025 — a long, undetected gap. Beyond CAT team's underlying bug fix, Tingyu is planning a TUDAS data-collection health monitor to catch this failure class (long silent upload gaps, likely IT-outage-driven) quickly going forward, rather than relying on users to notice and report it. Still in the planning stage — no design or target date yet.
