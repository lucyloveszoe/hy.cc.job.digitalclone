01/03/2025 architecture decision: SW team decided to remove all custom-built NTLM auth and route every auth need through BRCM OKTA, enforcing an "OKTA-only" guideline going forward (proposed by Kin Lum/Chao, in response to an OKTA-integration concern MUC/Martin raised 12/20/2024). Yu Han's framing: the incoming JWT "dual token" mechanism covers most of it, but raised an open question of whether to trust a developer's own code to collect OKTA credentials at a custom portal before relaying to the OKTA agent.

**Dual-token design**: (1) "ID.Pass" — a long-lived (6-12 month) JWT "bearer" token created once via Atropos after OKTA login, stored locally, consumed silently by desktop clients (zDB UI, pCD Client, Workflow UI) and API calls; (2) a short-lived (1 hour) JWT access token minted from ID.Pass via an on-premise API call that also pulls AD groups for role-based access. For fully-internal (BRCM-domain) scenarios, AD groups can instead be cached 1-24h to skip the 2nd-token round trip. For externally/publicly-deployed APIs used only by WSD's own tech stack, a Lambda rotates the access token hourly into AWS Secret Manager for shared consumption.

**Rollout as of 01/07/2025** (multiple parallel workstreams, target dates 01/31/2025 and 04/30/2025):
- **BRCM OKTA SSO Integration** (KinLum/YK/Ken, target 01/31/2025): Atropos is the 1st fully-OKTA-integrated site; created AD group TEAM-WSD-SWADMIN + OKTA group OM_WSD_SWADMIN (note: AD and OKTA groups are NOT auto-synced — GTO OKTA team's recommended pattern is to create/manage the group in OKTA/MUSSIC, then request GTO push it into AD); WSD.Jwt repo built (ID.Pass generator + access-token auth endpoint); ZDB UI, pCD site, and the wudas.sgn/wudas.lvn API endpoints being migrated off Atropos-membership login.
- **Secured OKTA-User Access to Sharable URL File** (Chao/Jiapeng, target 01/31/2025): a WSD.Utility.S3Proxy service that wraps an S3 object behind Windows/NTLM-style auth (curl --ntlm -u oktaid:oktapassword), checks OKTA ID + AD group authorization, then redirects to a 1-minute presigned S3 URL. Staged to wudas.sgn/lvn.broadcom.net; used by IDI and TAP integrations (which use the "ALL WSD" AD group by default, except PPYCC which needs its own AD group; IDI/TAP get "contractor level" integration to avoid repeated OKTA logins).
- **Secure API/Data Access by Dual (ID+Session) JWT Tokens** (KinLum/Chao, target 04/30/2025) and **Secure Internal API Call by Rotating JWT Token with AWS Secret Manager** (Tingyu, target 04/30/2025): both still "In Prep," scope/timeline adjusted based on the OKTA integration rollout above.

GTO's OKTA-application setup requires a GTO 1.SUPPORT ticket per app (register DNS/host name, apply a DigiCert TLS cert, request the OKTA application with a target audience e.g. Okta_Mastered_Division_WSD, then a separate ticket to push the OKTA group into Active Directory).

**Why:** a foundational, cross-cutting security architecture change affecting essentially every WSD web app/API (Atropos, pCD, zDB UI/API, ATA, IDI, TAP/TUDAS) — not a single-project item.

**How to apply:** treat "ID.Pass" and the dual-JWT pattern as WSD's standard auth mechanism going forward; check this file before assuming a WSD web app still uses legacy NTLM/Atropos-membership auth. Related but distinct: [[project-certificate-lifecycle-keyfactor]] tracks TLS certificate lifetime policy, not this auth architecture.
