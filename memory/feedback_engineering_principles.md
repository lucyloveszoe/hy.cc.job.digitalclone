Recurring working principles Yu Han applies when reviewing his team's technical proposals, drawn from weekly status reports (ww01–ww10, 2026):

- **No re-inventing wheels**: overlapping feature requests get redirected to existing tools rather than building new ones (e.g. an FCM comparison request was redirected to the existing Spec Portal). Why: avoids duplicate tooling investment. How to apply: when evaluating a new feature request, check for an existing tool/portal first.

- **Side-by-side testing before deciding**: when multiple technical candidates are being evaluated (e.g. a JSON memory-spike fix), Yu Han requires all candidates tested on the same dataset before a decision is made. Why: ensures a fair comparison instead of anecdotal results. How to apply: frame technical proposal reviews around "was this benchmarked against alternatives on identical data?" This goes back at least to 2023 (see [[project-2023-annual-review]]): the team benchmarked "tiny S3 segment files" vs. "single large binary + range access" before picking a Dev-Proto stitching design, and separately let the DS stakeholders vote MLFlow vs. Verta only after a hands-on POC of both.

- **Prefers cloud-managed services over self-deployed infra**: when choosing among DB backends (e.g. Impala/DuckDB/Trino for GD-Breakdown DB), he leans toward options that avoid the team owning ongoing deployment/maintenance. Why: reduces team operational burden. How to apply: weigh "who maintains this" heavily in infra recommendations.

- **Batches changes into planned upgrade cycles**: several improvements are deliberately deferred with "hold until next major upgrade" rather than shipped piecemeal (e.g. TUDAS SQLite migration held for the NXG TUDAS upgrade). Why: avoids disruptive incremental changes to systems due for a bigger overhaul anyway. How to apply: when a fix could be either a quick patch or bundled into an upcoming platform upgrade, default to asking which cycle he'd rather bundle it into.

- **Hands-on evaluation over vendor materials**: for security tooling (e.g. CloudSecure), he prefers arranging a live pressure-testing session over reviewing vendor marketing/technical docs. Why, in his words: "no need to deep dive... arranging a pressure testing session should help us better evaluate." How to apply: when assessing vendor tools/claims, suggest a hands-on test rather than a document review.

- **Architecture boundary discipline (Clotho/pCD)**: pushed back (09/09/2025) on a Wafer-team proposal that would have coupled test-process logic into the platform, restating the principle that Clotho = execution, TDG = test-plan logic, pCD = revision control, and these must stay decoupled. Why: keeps the platform generic and reusable across test types. How to apply: flag any proposal that couples a specific test process into Clotho/pCD core as against this principle. Reaffirmed by Kin Lum in ww21 (05/26/2026). See [[project-pcd-clotho-v7]].

- **80/20 ROI scoping over full-coverage discovery** (04/14/2026, re: pCD-V wafer/U-Portal discussion): stated projects shouldn't try to cover "ALL corner use cases" — apply the 80/20 rule for ROI. The goal is to improve efficiency/turnaround and reduce human error, not to preserve PE/TDG's existing manual process exactly. Why: avoids stalled, open-ended requirements-gathering. How to apply: when a discovery discussion starts chasing exhaustive edge-case coverage, redirect toward the 80/20 cut and the actual efficiency goal.

- **Minimum-footprint platform changes**: for the PAD Dynamic Sampling work, preferred solving the problem inside test-plan code using existing Clotho features over adding new engineering to Clotho itself. Why: consistent with the Clotho/pCD genericity principle above — keep the platform surface area small.

- **AI coding tool cost-routing policy** (confirmed 03/31/2026, restated repeatedly through ww22): default to Gemini over Claude for day-to-day Cursor coding work — "Gemini performs similarly to Claude in >90% of scenarios," and defaulting to Claude burns the shared monthly token quota too fast. Use "Plan with Claude, Build with Gemini" for complex architecture work. Per-user spend cap set at <$200/month. Why: cost control on a shared/capped Cursor token budget (see [[project-genai-program]] for the evolving budget figures). How to apply: when advising on Cursor/Claude/Gemini usage at WSD, default to this routing rule rather than "use whichever is best" — it's policy, not just a suggestion. Note: by ww31-33 (Aug 2026) Cursor itself is being sunset in favor of Claude Code, so this routing rule's Cursor-specific framing is becoming dated — see [[project-genai-program]] for the current tool landscape.

- **Vet "urgent" requests against actual usage before committing bandwidth** (recurring observation, ww26-30): Yu Han found multiple features rushed through as "urgent" (FCM Analyzer Outlier Removal, FCM-Telecaster-II, worst-case-snp) went unused afterward, forcing the team to cut corners for no payoff. He is building a vetting mechanism with Chao/Jiapeng to check real urgency/usage before fast-tracking a request. Why: repeated pattern of wasted rushed work. How to apply: when a request is framed as urgent, ask what evidence supports the urgency and who will actually use the result. This pattern recurs much earlier too: in a 01/07/2025 status report, Yu Han declined to fast-track a PE-requested PMDx PCB-strip Maverick-detection feature without ROI justification, explicitly citing past experience that some "urgent" PE-requested DPAT features were seldom used or retired soon after deployment — the same reasoning restated roughly 18 months before the ww26-30 (2026) episodes above.

- **Push back on over-engineered proposals in favor of production-friendly solutions** (08/2024, Tester-to-Tester Communication proposal): when YK's team proposed a generic, extensible "OEE dynamic tester grouping" solution (Kafka/MQTT/Redis-based) to solve a narrow Clotho1+Clotho2 communication need, Yu Han judged the proposal over-complicated and asked the team to trade off toward a simpler, more production-friendly but still reliable solution, holding further discussion until after internal cross-team alignment. Why: guards against solving a narrow problem with unnecessarily broad/complex infrastructure. How to apply: when a proposal introduces significant new infrastructure (a message broker, a new service) for a narrowly-scoped problem, check whether a simpler production-friendly option was considered first.

- **Formal, staged security-scan discipline over ad-hoc re-scanning** (Mythos program, ww29 onward): Round 1 full scan → owner fixes → Round 2 full scan → owner review/fix → Round 3 selected scan → done. Going forward, all new releases/upgrades go through a Mythos scan by default (skip-list reserved for explicitly flagged legacy projects). Why: replaces uncontrolled, repeated re-scanning with a predictable remediation cycle. How to apply: within each round, use Ken's specific delta-scan prompting pattern — scan finds set "E", fix it, then re-scan should be prompted to find only "E+x" (the incremental new findings against the known baseline), not treated as an uncontrolled fresh "A then B+y" re-scan from scratch each time — this keeps remediation cycles converging instead of re-litigating already-accepted findings. See [[project-mythos-security-scanning]].

- **One platform-wide auth/token mechanism, not one per requesting client** (02/04/2025, IDI OKTA integration): when the DA team asked IDI to adopt their own custom short-lived "DA-Token" instead of WSD's standard ID.Pass JWT, Yu Han declined — ID.Pass already covered DA's actual need (permission payload, trivial client change), and as the platform/API provider WSD should support one token mechanism across all apps/services rather than a bespoke one per client. Why: every client-specific exception multiplies the auth surface WSD has to maintain. How to apply: when a team asks WSD to support their own custom auth/token scheme, check whether the existing standard mechanism (ID.Pass / dual-JWT, see [[project-okta-sso-jwt-architecture]]) already covers the need before agreeing to a one-off.

- **AWS SDK "slow" symptoms can be a client-side retry-mode default, not a real AWS latency issue** (07/2023, AWS SDK Slow bug): AssumeRole/STS calls appeared to take 20-30 seconds; AWS support closed the case confirming STS itself wasn't slow — the delay came from S3Client instantiation. Root cause found by the team: when a machine has no default AWS CLI config file (`~/.aws/config`), the AWS SDK's `RetryMode` silently defaults to `Legacy`, which is slow due to reflection-heavy config object handling; explicitly setting `RetryMode` to `Standard` fixed it immediately. Why: an AWS-side support ticket can send you looking in the wrong place when the actual cause is a client SDK default that's invisible unless you go looking for it. How to apply: before escalating "AWS is slow" issues to AWS support, check the SDK's retry-mode configuration and whether a default AWS config file exists on the host. See [[project-2023-annual-review]].

- **AWS ECS/Fargate can silently fail to start a requested task, with no error surfaced to the caller** (09/03/2023 incident, DPAT outlier-file production halt): DPAT requested ECS to start a task processing a specific lot; ECS never started it — no exception, no callback failure — and both Inari and ASEKR production sat blocked for over a day before anyone noticed missing outlier files. AWS's own investigation found the root cause was a Fargate host-level "timeout waiting for network interface provisioning," an intermittent Fargate/API issue AWS itself suggested mitigating with exponential-backoff retry via Step Functions. Fix: stopped assuming ECS task-start requests are 100% reliable — added explicit retry/confirmation logic around ECS task requests in DPAT's core processing logic. Why: a request that "succeeds" from the caller's point of view (the API call returns without error) doesn't guarantee the requested work actually started — this is a distinct failure mode from a thrown exception. How to apply: for any ECS/Fargate task kicked off as fire-and-forget, don't trust the launch call alone — verify the task actually started (or add automatic retry) rather than assuming success. See [[project-2023-annual-review]].

- **AssumeRole sessions cap presigned-URL lifetime — use a dedicated minimal-permission user for long-lived presigned URLs** (recurring gotcha, Jan 2023, ContactorID Upgrade then WUDAS Top query): AWS caps an AssumeRole session at ≤12 hours, so any S3 presigned URL generated under an assumed role silently inherits that expiration regardless of the requested longer lifetime (WSD needed 5-7 day URLs). Fix applied both times: reserve a separate, minimal-READ-only IAM user (not a role) exclusively for presigned-URL generation, "switching in/out" that credential per API call rather than using the caller's assumed-role session. Why: the failure mode (URLs expiring early) is silent and easy to miss until users hit dead links days later. How to apply: whenever a design calls for long-lived S3 presigned URLs inside an AssumeRole-based architecture, flag this cap immediately and default to the dedicated-user pattern (or CloudFront, which the team also adopted for the same WUDAS case to avoid presigned URLs altogether for read-heavy paths). See [[project-2023-annual-review]].

- **S3 lifecycle/retention rules need an explicit exception path for "immortal" anchor files, not just a longer default** (11/21/2023 incident, STMicro StWafer detail): a blanket 1-year retention rule on a `prc.xx` prefix silently deleted a full-history header file that StWafer detail processing depended on indefinitely, breaking it with no alert until a user reported it. Fix: moved the anchor file into a dedicated no-lifecycle-rule bucket (the existing Atropos bucket) rather than trying to pick "long enough" retention numbers. Why: a retention policy tuned for genuinely disposable intermediate data will eventually catch a file that was never meant to expire, and the failure is silent until something breaks downstream. How to apply: before applying a blanket S3 lifecycle/retention rule to a prefix, check whether any file under it must persist for the life of the service — if so, give it a separate no-expiry location rather than a longer TTL. See [[project-2023-annual-review]].

- **Skip an intermediate upgrade if the target itself is heading toward EOL soon** (01/21/2025, .NET 6→8 migration): once .NET 6 hit EOL, the team paused most remaining .NET 6→8 upgrades rather than pushing them all through immediately — reasoning that .NET 8 itself goes EOL Nov 2026 while .NET 10 lands Nov 2025, so upgrading straight to 8 now would mean re-upgrading again soon after. Exception: upgrade immediately if a specific app is caught by a GTO security scan. Why: avoids a redundant migration cycle just to hit a soon-to-be-superseded intermediate version. How to apply: when a forced framework/version upgrade is proposed purely for EOL compliance, check whether skipping ahead to the next stable target (once available) avoids a wasted intermediate hop — unless a compliance/security scan forces the immediate version.

- **Don't maintain one-off internal front-ends long-term — invest in shared middleware/backbone instead** (FCM Analyzer sunset direction, ww33): for small-user-base desktop utilities, the team's direction is to deprioritize/sunset them, push domain experts to self-serve via Claude Code, or consolidate functionality into the central TUDAS Portal/Spotfire rather than maintain bespoke UIs. Why: SW team's leverage is in shared platform/backbone work, not maintaining many small custom tools. How to apply: when a request is for a new small single-purpose internal tool, check whether it should instead be a self-serve Claude Code task or a feature added to an existing central portal.

- **Bound open-ended/range-style API requests with concrete numeric caps, not just a "reasonable" design** (10/21/2025, zDB partial-zip-extraction API): when Ken's draft "list/download zip entries" API design flagged some access patterns as "aggressive" without hard limits, Yu Han also proposed a simpler alternative (a preview/selective-download web portal, since zip size and segment counts vary too much per file type for one clean API shape) and, in parallel, imposed explicit CAPs on the API path itself: ≤15 matched zip files, ≤3000 total matched entries, ≤3GB total matched size, plus a call-frequency limit (≤1 call/3s or ≤20 calls/60s) for the listing API. Why: an API that accepts an open-ended range/pattern query can be triggered into unbounded backend cost by a single caller; a numeric CAP forces that cost to stay bounded regardless of caller behavior. How to apply: when reviewing a proposed API that accepts a range, wildcard, or pattern-style query against variable-sized backend data, ask for concrete CAPs (result count, total size, call frequency) rather than accepting "we'll validate it's reasonable" as sufficient design.
