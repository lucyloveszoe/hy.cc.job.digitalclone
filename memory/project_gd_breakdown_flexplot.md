Ongoing architecture POC for the GD-Breakdown "Detail" style DB / "Flex-Plot Prototype," evaluating Apache Iceberg + Trino + S3 vs. Snowflake + S3 as the storage backbone. Target milestone noted as 3/27/2026.

Yu Han has flagged this internally as a likely cornerstone for integrating future FCM ATE data into TUDAS/FCM workflows — i.e. a strategic dependency, not just a POC in isolation.

**Resolved architecture decision**: dropped the Parquet/External Table approach; standardized on loading CSV directly into Snowflake (a large table — cited as ~14B rows, 120 columns — requiring re-parsing of existing data).

**Timeline reached production**: Flex-Plot Phase 1 Trial Release launched 03/17/2026 (Ken); reached official production release 04/07/2026 at flexplot.wsd.broadcom.net with SSL and AuthHub login integration; a usage/cost review was scheduled for 05/10/2026. Finalized 3-tier architecture: Tier 1 = FlexPlot (released), Tier 2 = GD-API (CSV into Snowflake per above), Tier 3 = NXG-WUDAS (Chao completed processing 180K production files as of 02/26/2026).

**FCM-Telecaster-I: likely direct precursor to FCM Analyzer V1.1.0 (Oct-Dec 2025)**: an urgent request from Mitchell/Ricardo (SJ FCM) and David (CAT) to upgrade FCM Analyzer so it can generate Telecaster FCM data statistics for Lago RFEB-1.5 — Chao/Jiapeng built a hybrid worker + web API to auto filter/align/stitch TAP+Telecaster data against a customer spec ID, run pre-processing (outlier removal), and export results via an Excel template (PPYCC-style). By 12/02/2025: Telecaster data flowing into TUDAS via a new `tele-submit.exe` tool, FCMAnalyzer UI (payload edit/validation, WC-result display, task-history management, Excel export) complete, 1st demo delivered to the FCM team, 2nd demo scheduled — target was Beta 11/24/2025 (hit) and Official release 12/05/2025. Long-term plan (agreed with CAT/FCM): expand TapCollector to MacOS for full Telecaster automation (no manual `tele-submit.exe` runs), and always collect/process the full Telecaster folder. Treat this as the direct predecessor project to the FCM Analyzer V1.1.0 release described below — same tool, same team (Chao/Jiapeng), continuous development thread. **FCM-Telecaster-I marked Complete (12/09/2025)**: production API/worker and TUDAS website/Cloud Engine upgraded to production, FCM Analyzer program upgraded to the production database, all reported bugs fixed, and a 2nd larger-group beta demo held — officially closed. A follow-on **"Support FCM-Telecaster-I Evaluation"** effort started the same week: David got Haas Proto-2 Telecaster data into TUDAS, Ming is teaching Chao/Siva to build API JSON from David's result files, and Mitchell is arranging a work-group session to run the workflow using the newly created filters/specs. **This evaluation itself marked Complete (12/11/2025)**: the work-group session ran successfully using real Haas data compared against manually-extracted results; ongoing FCM support work rolls into a new umbrella, **"TUDAS-EX1 + TUDAS/FCM Upgrade Cycle"** (Tingyu/Jiapeng/Chao), which also absorbs the separate MacOS/Telecaster expansion (TUDAS-EX1) and a backlog of smaller improvement requests collected during the FCM-Telecaster-I build — still pending a workload estimate/schedule as of 12/16/2025. **GD-Breakdown POC: weekly status review begins, early technical experiments (12/16/2025)**: Ken started experimenting with the Lago data — running GoldenEagleConsole with a customized `ParameterKeywords.txt` without needing Windows, aggregating data by its `param` column (Chao's idea), and trying a Parquet format for the flattened data. All in-progress; no result yet.

**Architecture direction from Yu Han (12/23/2025)**: converting all NPI data files to a fixed ~70-column layout (GD-category max count + system columns + 6 extra fields); converting CSV→Parquet doesn't meaningfully change file size either way; a set of per-raw-file Parquet files can already support local ad-hoc charting queries. **To-do**: evaluate an Impala- or DuckDB-style engine (both use Parquet as their backing storage format) for large-scale query — preferring a cloud-managed service over one WSD has to deploy/maintain itself.

**"TUDAS-EX1 + TUDAS/FCM Upgrade Cycle" gets a target date and starts landing fixes (12/23/2025)**: target set to **02/20/2026**. TUDAS's Worst-Case-Study portal/API and worker both upgraded to match the FCM worst-case-study worker (new filter-JSON fields, duplicate-spec-record support) — both Complete. Chao started building the FCM Analyzer setup for the Largo project (In Progress). General bug fixes: a Feeder Lambda trigger failure under AWS-support investigation, and a CID-parsing bug for special characters (e.g., "Cliff's Bench") that was breaking web-API collection-progress reporting — the tag-link-sharing half of this fixed, the collection-progress half still in progress.

**Workflow validated; a real production-risk finding surfaces (12/30/2025)**: Ming Bao successfully created a worst-case-study payload from the TUDAS portal and copy/pasted it directly into the FCM Analyzer program with no manual editing — validates the intended zero-manual-step workflow for the Largo project. A "collector API using anonymous authentication causes an exception" bug was fixed. **New finding, still open**: large result-file JSON serialization/deserialization triggers a momentary memory spike far above the file's actual final memory footprint — a few hundred MB of JSON caused a spike up to **14 GB**, severe enough to bring the system down. Chao is designing a new parser (and writing a test partitioning function) to handle large result files without this spike — in progress, not yet fixed. Treat this as a standing reliability risk for any large-result-file workflow until the new parser lands.

**Origin traced to Sep-Nov 2025**: this began as Ken's "Flex-Plot" proposal — using GE to break each Clotho ATE result file down into a fixed-column sparse CSV square, appended to an interim DB for flexible ad-hoc search/comparison (an alternative/complement to Spotfire and PADMA) — first drafted as an SOW/SRS on 10/02/2025. A kickoff session with SJ NPI (Steven's team) and JJ's team (the PADMA owner) on 11/23/2025 led to agreement (11/25/2025) to build a GD-Breakdown-DB-based POC, owned jointly by SW's Ken and SJ NPI's Kevin, with a **demo targeted for 01/30/2026** — the goal being to prove the GD-Breakdown DB format can support the needed data access within acceptable latency/cost. This is the direct precursor to the Iceberg/Trino-vs-Snowflake architecture POC and the 03/17/2026 Trial Release described above. **Ownership split clarified (12/02/2025)**: Chao leads the DB design specifically, while Ken remains overall POC owner; pending a clarified DB design proposal from Chao.

**Why:** the storage-architecture choice made here is expected to shape a downstream, higher-stakes integration (FCM ATE data into TUDAS).

**How to apply:** treat any resolution of the Iceberg/Trino vs. Snowflake question here as directly relevant to future FCM/TUDAS integration planning. Project has moved from POC to a live production tool — future updates should track usage/adoption/cost, not architecture selection.
