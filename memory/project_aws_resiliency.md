Yu Han initiated the "WSD/AWS Resiliency Improvement" effort after an AWS us-east-1 outage, because WSD's major workloads run in an older-generation SG (Singapore) AWS region. This has been an active, recurring theme across every weekly status report from ww01 (Jan 2026) through ww10 (Mar 2026).

**Origin actually traces back a full year earlier, to 11/17/2025** — not ww01 2026 as the framing above implies. The 2025 weekly report explicitly cites "the recent AWS us-east-1 down issue" as the trigger for Yu Han requesting this discussion, with Kin Lum driving an initial round using **pCD as the pilot project**: S3 multi-region replication, API Gateway + Route53 multi-region smart routing, Aurora (dynamic PostgreSQL global endpoint across region replicas), and EC2 multi-region mirrored AMIs — pending AWS follow-up. Yu Han also flagged other mission-critical projects that need the same resiliency review: Cloud SFTP (YK/Choo-Yau), AppRunner/TUDAS (Jiapeng), ECS/ECR (PRDA/DPAT, Kin Lum), and Snowflake (Kin Lum). Treat this 2025 kickoff as the same initiative that becomes the recurring ww01-ww10 2026 theme above, just over a year earlier than previously recorded — update this note if a later report explains the ~14-month gap between this kickoff and the 2026 activity.

Scope: a multi-region resiliency review spanning S3 (multi-region), Route53, Aurora (global endpoints / failover), and multi-region EC2/AMI options, applied across several of WSD's mission-critical projects.

**Why:** named as a direct response to a real outage impacting older-region infra WSD depends on — this is risk-driven, not routine hardening work.

**How to apply:** treat this as a live, multi-quarter initiative Yu Han is personally driving. Status updates on it (region migration decisions, Aurora failover guarantees, etc.) should update this file rather than create a new one. As of ww01, one open unresolved question was whether AWS provides any vendor guarantee for Aurora private-IP retention on failover — flagged as needing GTO alignment.

Likely the same unresolved question referenced generically above — reconcile if a definitive resolution is later found.

**pCD Daemon/Xfer "stuck" incident at Chipbond, root cause found (06/24/2025)**: pCD Daemon and Xfer services at CB got stuck (<1hr) inside `SecretManagerAccessTokenProvider`/`HeartBeatReporter`; forced restart resolved it immediately. Root cause: AWS Secrets Manager client creation with an assumed role could hang indefinitely. Fix (deployed 06/20/2025, monitoring 1-2 weeks): explicitly set `AmazonSecretsManagerConfig.DefaultConfigurationMode` to Standard, plus a 60s retry/timeout when `new AmazonSecretsManagerClient()` doesn't return. A new reliability failure mode for anything using assumed-role Secrets Manager access — relevant to the broader credential-rotation work in [[project-mythos-security-scanning]].
